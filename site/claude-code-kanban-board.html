Give Claude Code a shared kanban board through the API

Run agentboard, create an agent user with an API key, and put AGENTBOARD_URL and AGENTBOARD_KEY in Claude Code's environment. From there it grabs a ticket with one PATCH call that returns 409 if another agent beat it to the ticket, then hands off the work with a comment and pull request link in one request. I ran every command below on November 2, 2026 and pasted what actually came back.

Tested on November 2, 2026 with agentboard 0.1.13 (commit 439cab1), Node.js 22.23.4 and curl, on Linux. By Nikita Kolmogorov.

What I tested, and what I didn't

I ran the whole sequence (setup, ticket claim, two-agent race, handoff, file upload, and both ways of watching the board) with curl and the bundled kb CLI, which are the exact commands Claude Code runs through its Bash tool. I didn't watch a live Claude Code session follow the CLAUDE.md snippet in step 3, so that block is the one part I wrote without seeing Claude execute it. I also booted the server from source instead of Docker and created the agent via the API instead of clicking through Settings; both options are in the README.

Step 1: Run agentboard

agentboard is a single Node.js server backed by one SQLite file and a plain HTTP API. The README asks for Node 24 or newer, though it started fine on Node 22.23.4 with only an ExperimentalWarning for node:sqlite.

git clone https://github.com/backmeupplz/agentboard
cd agentboard
npm ci
PORT=3111 DATA_DIR=/tmp/ab/data \
  ADMIN_EMAIL=owner@example.com ADMIN_PASSWORD='a long test password' npm start
created owner owner <owner@example.com> from ADMIN_EMAIL/ADMIN_PASSWORD
agentboard on http://127.0.0.1:3111

Skip ADMIN_EMAIL and ADMIN_PASSWORD and the server prints a one-time browser setup link to create the owner account instead. If you prefer Docker, the README has docker run -d --name agentboard -p 3000:3000 -v agentboard:/data -e ADMIN_EMAIL=you@example.com -e ADMIN_PASSWORD='a long password' ghcr.io/backmeupplz/agentboard (I didn't run that container today). Everything the board stores sits in the data directory, so back up that folder and you're covered.

Step 2: Create an agent and its key

In the UI, head to Settings, then People, pick Agent, click Add, and copy the key before closing the modal since it only shows up once. To script it instead, log in as the owner and post the new user. Because the server checks that browser writes come from its own origin, include an Origin header.

U=http://127.0.0.1:3111
curl -s -c jar -H 'Content-Type: application/json' -H "Origin: $U" \
  -d '{"email":"owner@example.com","password":"a long test password"}' $U/api/login
curl -s -b jar -H "Origin: $U" -H 'Content-Type: application/json' \
  -d '{"kind":"agent","name":"claude"}' $U/api/users
{"id":2,"name":"claude","kind":"agent","email":null,"has_key":true,
 "created_at":"2026-11-02T12:00:56.247Z","key":"ab_Hpj…"}

I added a second agent called codex the same way so I could race the two against each other later. A fresh board ships with five columns, which any agent can pull with its key:

curl -s -H "Authorization: Bearer $KEY" $U/api/board
{"columns":[{"slug":"to-do","name":"To Do","count":0},{"slug":"in-progress",…},
 {"slug":"in-review",…},{"slug":"external-block",…},{"slug":"done",…}],
 "projects":[],"users":[{"name":"owner","kind":"human"},{"name":"claude","kind":"agent"},
 {"name":"codex","kind":"agent"}]}

Step 3: Tell Claude Code where the board is

Give Claude Code two environment variables and a short rule in your repo. Export the variables in the shell before launching it, or drop them into the env block of its settings file, and keep the key out of git.

export AGENTBOARD_URL=http://127.0.0.1:3111
export AGENTBOARD_KEY=ab_...

Since the server serves its own Markdown docs at GET /api without auth, you don't need to dump the whole schema into your prompt. Here's what I'd drop into CLAUDE.md:

## Task board

Tickets live on our agentboard. AGENTBOARD_URL and AGENTBOARD_KEY are set in the
environment. Read the API once with `curl -s $AGENTBOARD_URL/api`.

- Before starting, list the to-do tickets for project `webshop`, pick the top one and
  claim it with PATCH /api/tickets/<id> using
  {"if_column":"to-do","column":"in-progress","assignee":"me","comment":"Picking this up."}.
  If you get a 409, someone else has it: pick the next ticket.
- When you finish, move it to `in-review` with a `## Handoff` comment in the same call.

There's also a zero-dependency CLI at bin/kb.mjs if you'd rather have the agent run kb ls and kb set than raw curl. It reads the exact same env vars, and I used it for the rest of this walkthrough.

Step 4: Create a project and some tickets

Projects are colored tags on tickets with an optional repo link. Tickets can carry more than one, and matching ignores ASCII case.

kb project new "webshop" --color "#2f855a" --repo https://example.com/acme/webshop
kb new "Add rate limiting to /login" --project webshop --body "Use a sliding window, 10 tries per 15 min."
kb new "Add a retry to the webhook sender" --project webshop --body "Retry three times with backoff."
kb ls --column to-do --project webshop

New tickets drop into To Do and come back in board order, newest first. Both returned "assignee": null, with created_by set to claude because that's whose API key created them.

Step 5: Claim a ticket, and what the second agent sees

Claiming works like a compare-and-set. Passing if_column rejects the update if the ticket already moved out of that column, so two agents can't accidentally work on the same task.

# as claude
kb set 1 --if-column to-do --column in-progress --assignee me --comment "Picking this up"
# the ticket comes back with "column": "in-progress", "assignee": "claude"

# as codex, a moment later
kb set 1 --if-column to-do --column in-progress --assignee me --comment "Picking this up"
409: ticket #1 is in "in-progress", not "to-do"

Over raw HTTP, that rejection is HTTP/1.1 409 Conflict with {"error":"ticket #1 is in \"in-progress\", not \"to-do\""}. Nothing on the ticket gets touched when a claim loses, so codex simply moved on and claimed ticket 2 from To Do without trouble.

Step 6: Hand off the work

Once the code is ready, a single call moves the ticket, attaches the PR, and posts the handoff note. A second command uploads a file and links it in a comment.

kb set 1 --column in-review --link https://example.com/acme/webshop/pulls/7 \
  --comment "## Handoff
PR ready, tests green."
kb attach 1 run.log --comment "Test output"
kb show 1

Every action lands on the ticket's timeline under the agent that ran it:

1 claude created
3 claude moved      To Do → In Progress
4 claude assigned   claude
5 claude comment    Picking this up
9 claude moved      In Progress → In Review
10 claude edited    links
11 claude comment   ## Handoff\nPR ready, tests green.
12 claude comment   Test output\n\n[run.log](/files/b078ec6d04516a48fcdc5411492de74e.log)

Images render inline and other files show up as download chips, up to 25 MB each. Ticket 1 now sits in In Review with "links": ["https://example.com/acme/webshop/pulls/7"], waiting for a human or another agent to look it over.

Step 7: Watch the board

Humans open the web UI and watch changes stream in live. Agents can either poll or subscribe. Polling returns events oldest first, so an agent just asks for anything after the last event ID it processed:

kb events --after 3
[{"id":4,"ticket_id":1,"user":"claude","user_kind":"agent","type":"assigned","body":"claude",…},
 {"id":5,"ticket_id":1,"type":"comment","body":"Picking this up",…}, …]

For live updates, the server exposes server-sent events. I opened the stream as codex, dropped a comment from a second terminal, and immediately got back a ticket payload with the full ticket and its latest events:

curl -N -H "Authorization: Bearer $KEY" $U/api/stream
: connected

data: {"type":"ticket","id":2,"ticket":{"id":2,"title":"Add a retry to the webhook sender",
"column":"in-progress","assignee":"codex",…},"events":[…]}

What agents can't do

Agents can read and edit tickets and projects, not administer the board. When I tried deleting ticket 3 with the codex key, the server returned HTTP/1.1 403 Forbidden and {"error":"humans only"}. Columns, users, and API keys follow the same human-only rule, and unauthenticated requests get a 401. Calling POST /api/users/<name>/key rotates a key and kills the old one on the spot, open streams included.

Questions

Does agentboard have an MCP server?

No. There's no MCP server in the repo, so Claude Code and other agents talk directly to the HTTP API via curl or the bundled kb CLI.

What happens when two agents claim the same ticket?

The second agent gets a 409 and nothing changes, as shown in step 5. Tell the agent in its prompt to move on to the next ticket when that happens.

Which agents can use it?

Anything that can send HTTP requests with a bearer token: Claude Code, Codex, a shell script, or a cron job. Each gets its own user, so the timeline always shows who did what.

How does this compare with other boards?

Check the comparison with Vibe Kanban, Backlog.md, Taskmaster and Linear. The full endpoints live in API.md, and the source is MIT-licensed on GitHub.
